# VP9 硬件解码参考评估（vithalchowdary/NootedRed）

> 本文是一次**只读评估**的记录，不含任何被评估仓库的代码副本。结论基于对该 fork 的完整 clone
> （`/Volumes/XWorkspaces/Workspaces/GitResources/opensource/reference/NootedRed-vithalchowdary`，
> 浅克隆 master `6b36d5762e7c6aecee683aee1f071b4a5db1eaa5`，Release v1.3.1）逐文件阅读，
> 以及对本机两台实机 dyld 共享缓存 UUID 的实测比对。

## 1. 结论摘要

1. 该 fork 的 VP9 是一个**用户态共享缓存补丁**，不是 VCN 驱动新路径：它在
   `AMDRadeonVADriver2` 镜像里把"未使用的 AV1 处理空间"当作注入区，就地写入一段预编译后端字节，
   再改写 5 处能力/工厂/命令构建站点 + 20 余处 AV1 区域入口，让 `AvdCapability` 广告 VP9 能力、
   `VAFactory` 生成 VP9 处理器、`ProcessVcnCreateDecodeSession` 用新的 codec id 建会话；
   打补丁的动作在 `_shared_region_check_np` 钩子里对每个进程 map 做 COW 事务完成。
2. **数据与我们的机器精确对齐**：他们数据表内置的 `CacheUUID` 与我们两台实机实测一致——
   - Darwin 23 数据集 `4C1441FD8A543DC2863D49110B946A25` = work1 上 14.8.9/23J631 缓存 UUID；
   - Darwin 25 数据集 `5A3DA575F02E33DC9B14F663050011E6` = 249 上 26.7.3/25G342 缓存 UUID。
   也就是说，这份补丁数据就是在这两个 OS build 上生成的，不存在"版本对不上"的障碍。
3. **但后端源码没有开放**：数据头写 `Generated by tools/build_vp9_decode_patch.py from
   tools/vp9_backend/VP9Backend.cpp`，而 master 树里这两个文件都不存在（`tools/vp9_backend` 返回 404）。
   仓库只有 14,591 行 C++ 数据表（其中 14,000+ 行是机器码字节），没有可审计、可再生成的后端实现。
4. 仓库自带的 VP9 代码**无法原样复现构建**：clone 后 `xcodebuild` 失败在
   `Lilu/Lilu/Library/plugin_start.cpp`（工程引用的 Lilu 目录不在仓库里、也没有 `.gitmodules`），
   所以"拉下来编译一个 kext 直接试"这条路走不通，必须先补齐 Lilu 才能谈实机验证。
5. 因此建议：**借鉴基础设施与验证方法，不整包移植后端**。优先级见第 4 节。

### 2.2 运行机制

1. `init()`：仅 Darwin 22–25 启用；`-NRedNoVP9` / `-NRedNoVDA` 直接关闭；分配 `stateLock` 与
   一个 `Plan`（栈外，堆上，`StateSize=0xE8`、`PageCount=10`）。
2. `processPatcher()`：要求 `hasVCN0 == true`、`vcnGeneration == kVcn2_2`、无独显；解析
   `_get_task_map` / `_mach_vm_region_recurse` / `_copyin` / `_copyout`；路由
   `_shared_region_check_np` 与 `_vm_map_destroy`，任一失败即整功能关闭（`NRedVP9State=3`）。
3. 每次进程建立共享区域后：读 `dyld_v1` 头取 UUID → 与数据集 `CacheUUID` 比对 →
   解析 12 个函数站点（整函数字节 + rel32 引用双向校验 + `SectionTargets` 跨节目标 + `ABISlots` 结构偏移校验）
   → 对当前进程 map 做 COW（`collectPages` / `leafProtection` / `makeWritable`），逐站点写 `Patched`
   字节并回读校验；任一失败即回滚并**整个 boot 关闭 VP9**。
4. 全部站点写成功后发布能力（`VP9Probe`）：`IOGVAXDecode="2"`、`IOGVAVP9Decode="1"`、
   `IOGVAVP9DecodeCapabilities` 内 `VTSupportedProfileArray={0,2}`（Profile 0/2），
   三步中任一步失败就把已写的键撤回，避免"广告了能力但后端没装上"。
5. 观测点（IORegistry，便于我们直接复用命名）：`NRedVP9State`(0=Off/1=Resolving/2=Ready/3=Failed)、
   `NRedVP9Applied`、`NRedVP9Already`、`NRedVP9Mixed`、`NRedVP9LastVMError`、
   `NRedVTDecoderAdmissionRevision`。

### 2.4 风险

1. **钩子重入**：`shared_region_check_np` 内 `copyin` 读 dyld 缓存，缺页时可能重入同一个钩子。
   他们用 `State::Resolving` 闸门 + 堆分配工作区规避（与我们 10 月踩过的 double fault 教训一致），
   这条经验对我们是现成的对照。
2. **每进程 COW**：WindowServer、浏览器、解码器进程都要打一次；他们用 128 slot 的 map 记录表 +
   `vm_map_destroy` 钩子回收入场，属于必要开销，不适合放到高频路径。
3. **能力广告是全局的**：只要三条键发布出去，所有播放器都会尝试 VP9；若后端在某进程失败而未撤回，
   会出现"能选 VP9 但解不出来"。他们的 all-or-nothing 撤回是唯一缓冲，我们若移植必须保留。
4. **不可审计**：后端是预编译字节，声明来源 "Mesa port, MIT"，但 Mesa 代码本体不在仓库，
   无法核对许可与实现；作为下游发布时要自行承担这部分风险。

## 4. 建议路径

**Phase 0（0.5 天，已完成）**：clone + 逐文件评估 + 缓存 UUID 比对。产出即本文。
结论：数据完全对得上我们的两台机器，障碍只剩"后端源码不可审计"和"Lilu 缺失导致对方仓库不可构建"。

**Phase 1（1–2 天，只读，零风险）**：用对方的解析思路在我们真实缓存上做离线验证——
把 `Patches[]` 的 12 个站点与 26.7.3 / 14.8.9 两份缓存的字节逐一对上（只读文件、不装 kext）。
产出：确认"他们的数据可以直接套用我们的两个 OS build"，还是需要重新生成数据。
这一步不引入任何内核改动，失败也只是评估结论。

**Phase 2（3–5 天，可回滚）**：若 Phase 1 通过，移植"resolver 扩展 + 数据表 + `VP9UserPatch`"
到本仓库，`DeviceProfile` → `NRed::getDeviceID()` + `VCNCapabilities`，`VCNBridge::userPatchesAllowed()`
→ 自建"VCN 桥已就绪且非独显"门；新增显式开关 `-NRedVP9`，默认关闭；保留对方的状态属性名，
便于对照日志。

**Phase 3**：work1 14.8.9 与 249 26.7.3 分别验证（`NRedVP9State=2`、`NRedVP9Applied>0`、
VT 会话是否真正落到 VCN、`vdec_mode.swift` / Chrome 侧表现），异常即换回上一个 kext。

**不建议**：把 14k 行数据表直接塞进主线并默认开启；能力键先行发布而等后端；在没有 Phase 1
字节验证的情况下实机试。

## 落地实现（本仓库 `analysis/vp9-reference`）

- `tools/gen_vp9_sites.py`：把参考数据集里的“站点偏移 + 原始字节 + 补丁字节”转换为本仓库可用的
  纯字节表。生成时以本机真实 dyld 缓存为准做三级定位（数据集偏移仅在字节完全吻合时采信 →
  目标镜像 __TEXT 内唯一命中 → 全缓存唯一命中），校验主缓存 UUID 后才产出，任何站点不唯一即报错退出。
  结果：Darwin 25（26.7.3 / 25G342，UUID `5A3DA575F02E33DC9B14F663050011E6`）29 个站点全部唯一解析，
  输出 `NootedRed/UserVP9SitesDarwin25.hpp`（偏移相对主缓存 unslid 基址）。
- `NootedRed/UserVP9.cpp`：在 `_shared_region_check_np` 回调（由 `UserSurfaceSync` 转发，复用同一个
  已安装的钩子，不重复路由系统符号）里对**当前进程**的共享缓存副本做 COW 安装：
  先按最小站点探读判断本进程是否真的映射了 `AMDRadeonVADriver2`（未映射直接跳过，避免全系统进程都做
  26 KB 读写），再逐站点校验原始字节，全部原始状态才整批写入，任一站点不符即整轮放弃；
  写入失败回滚已写站点并恢复页权限。全部成功后通过 `IOService` 匹配 `IODVDBundleName == AMDRadeonVADriver2`
  的加速器服务发布 `IOGVAXDecode="2"`、`IOGVAVP9Decode="1"`、`IOGVAVP9DecodeCapabilities.VTSupportedProfileArray={0,2}`；
  不匹配/写失败则撤回能力键，保持软解可用。
- 观测属性（写在 IGPU 上）：`NRedVP9State`（0=Off 1=Resolving 2=Ready 3=Failed）、`NRedVP9Applied`（已安装进程数）、
  `NRedVP9Published`、`NRedVP9Withdrawn`、`NRedVP9MismatchSite`、`NRedVP9UUIDMismatch`、`NRedVP9LastVMError`。
- 首飞门槛：必须显式 `-NRedVP9` 才启用（`-NRedNoVP9` 强制关闭），默认不改变现有系统行为。
