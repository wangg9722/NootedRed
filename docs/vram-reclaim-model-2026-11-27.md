# macOS 显存回收机制实测（14.8.9 / Renoir APU / NootedRed）

日期：2026-11-27　分支：`nred/vram-alloc-fallback`（master `0e256c2` + `-NRedAllocPagesUnderflow` + `-NRedVRAMAlloc`）
目的：回答"显存到底怎么回收"，并检验"驱动没做回收"这一假设是否成立。

## 1. 结论先行

1. **回收机制是工作的，而且在工作。** 11-21 至 11-25 全天 `Failed to allocate` 计数为 **0**，同一台机器、同一套硬件连续使用；失败从 **11-26 10:49:38** 才开始出现。所以"连续跑一周没问题"是有日志支撑的事实，不是错觉。
2. **显存不是"用着用着漏掉"，而是三池结构：** 自由池（薄）、在用池、**孤儿可复用池（最厚，约占 2/3）**。三个池加起来恒等于固定区总量 3072 MB。
3. **失败不是"没内存"，是"取不到符合粒度/域的连续块"。** 失败样本里反复出现"请求 2.6 MB，当时 free 66 MB"这类不等式——请求远小于空闲仍失败，这是空洞形态/对齐问题，与本分支 `-NRedAllocPagesUnderflow` 修的是同一族病灶，与总量无关。
4. 因此：**"驱动不做回收"的假设被日志否证**；真正要解释的是"什么负载/什么代码路径会让中大型连续请求落不下"。

## 2. 三池构成（实测）

单卡读数（同一次采样，去掉 `PerformanceStatisticsAccum` 与其它伪加速器条目的重复）：

| 池 | 字段 | 数值 | 占比 |
|---|---|---|---|
| 在用 | `inUseVidMemoryBytes` | 948 MB | 31% |
| 自由 | `vramFreeBytes` | 82 MB | 2.7% |
| 孤儿可复用 | `orphanedReusableVidMemoryBytes` | 2045 MB | 66.6% |
| 孤儿不可复用 | `orphanedNonReusableVidMemoryBytes` | 0 | 0 |

合计 3075 MB ≈ `VRAM,totalMB = 3072`。**自由池长期只有 2%–3%**，不是异常，是设计：分配优先命中孤儿缓存。

> 读数陷阱：每个加速器会把同一份统计同时挂在 `PerformanceStatistics` 与 `PerformanceStatisticsAccum` 下，且系统里还有多个伪 `IOAccelerator` 条目（`IOCompatibilityProperties` 里那个 `vramFreeBytes=15728640`、`VRAM,totalMB=16384` 的是假的）。直接 `grep | 求和` 会得到"孤儿 4.2 GB > 总显存 3 GB"的荒谬值。正确做法是按数值指纹去重 + 只认带 `gartSizeBytes` 的那条。

## 3. 回收机制的实测行为

采样脚本 `/tmp/vramtrace.py`（1 秒粒度，去重后取真实加速器），三段追踪：

| 阶段 | 时长 | 现象 |
|---|---|---|
| A 空闲 | 90 s | 孤儿池在 2100–2200 块之间抖；`free` 全程卡在 **71–84 MB**，不回升 |
| B 持续 4K 硬解（12 轮 seek） | 22 s | 孤儿 2202→2154 块，`free` 96 MB，`inUse` 稳定 890–908 MB；**没有新增大块占用**，解码 surface 直接复用缓存 |
| C 解码进程退出后 | 45 s | `free` 56–104 MB 波动，孤儿 2026–2150 MB；**释放的 surface 没有变成 free** |

关键观察：

- **释放路径是「在用 → 孤儿」，不是「在用 → 自由」。** 进程退出、解码结束都不会把空间还给自由池。
- **孤儿池有增量清扫：** 单次约 20–50 块、60–90 MB，间隔不规则（实测 3 s – 47 s），空闲与负载下都会发生。这解释了为什么 `free` 能一直维持在几十 MB 而不枯竭——清扫只补足到"够下一批请求"的量。
- **复用命中率是动态的：** `orphanedReusableVidMemoryHitRate` 实测在 60% / 73% / 75% / 79% / 86% / 87% 之间变化，不是固定值。命中即"孤儿块被新分配直接拿走"，不经过自由池。
- **淘汰路径从未启用：** `vramEvictionWaitTime = 0`、`textureVolunteerUnloadBytes = 0`、`surfaceBufferPageOutBytes = 0`。也就是说这台机器上从来没有走到"把显存内容换出/驱逐"那一层——所有压力都在"连续块能不能凑出来"这一层被消化。
- **内核侧无日志：** 本开机全部 kernel 日志里没有任何 evict / purge / reclaim / vram pressure 记录。回收是静默的，不可通过日志直接观察，只能通过计数器推断。

## 4. 关键反证：历史上失败计数为 0

统一日志跨重启保留，按天统计 `process == "kernel" AND eventMessage CONTAINS "Failed to allocate"`：

| 日期 | 条数 |
|---|---|
| 11-21 | 0 |
| 11-22 | 0 |
| 11-23 | 0 |
| 11-24 | 0 |
| 11-25 | 0 |
| 11-26 | 30 610（首条 10:49:38） |
| 11-27 | 5 494（截至 11:14 崩溃） |

11-26 按小时：10 时 1148 / 11 时 2075 / 12 时 5093 / 13 时 3365 / 14 时 4743 / 15 时 3416 / 16 时 4491 / 17 时 5205 / **18 时 14 / 20 时 8** / 21 时 547 / 22 时 503。

两个含义：

1. 这台机器在 11-21～11-25 是**健康的**，回收机制完全跟得上；
2. 失败强度与**解码负载**同步——18–20 时几乎归零，说明不是常驻泄漏，而是"有视频解码/大块申请时才会撞上碎片"。

## 5. 由此建立的模型

```
客户端申请 → 优先从孤儿可复用池命中（hitRate 60–87%）
           ↓ 未命中
        自由池（长期仅 2–3%，靠增量清扫维持）
           ↓ 仍不够（含碎片/域/对齐不满足）
        allocateLargeBlocks 首次尝试失败 → 日志 "Failed to allocate"
           ↓
        [R2] 逐级回退：非可见域连续 → 可见域连续 → 非可见域非连续
                        → 全 UMA 域连续/非连续 → 16K/4K 细粒度非连续
```

- 孤儿的"厚"不是泄漏，是**复用缓存**；它占了 2/3 显存，靠 hitRate 支撑日常分配。
- 自由池的"薄"是结果不是病因：清扫按需补，够用就停。
- 失败发生在"连续大块 + 固定区内碎片"这一层；`R1` 修空洞算术、`R2` 给回退，两者都在这一层，方向正确。

## 6. 与实验分支的关系

| 配置 | 同场景失败数 | 结论 |
|---|---|---|
| 11-26 的构建（`66a793f6`，无本分支两个开关） | 11-26 一天 30 610 条；11-27 崩溃前 3 608 条/小时 | 有症状 |
| master + R1 | 41 分钟 636 条，仍在刷 | R1 单独不够 |
| master + R1 + R2 | 9 分钟含 4K 8 次 seek 压测：**0 条** | R2 覆盖住症状 |

注意：R2 是"换域/换非连续"把请求塞进去，不是让连续块重新够用。孤儿池仍有 2 GB，说明碎片结构没变，只是被绕开。

## 7. 待验证（下一步）

要判定"11-26 之后到底哪一处把连续大块弄没了"，用同一套压测脚本做三档对照，一次只差一个变量：

1. 构建 A：纯 master（两个开关都不开）
2. 构建 B：master + `-NRedAllocPagesUnderflow`
3. 构建 C：master + 两个开关（当前）

判据：跑同一段 4K 硬解 + 8 次 seek 循环 5 分钟，统计 `Failed to allocate`、`vramFreeBytes` 谷值、`orphanedReusableVidMemoryBytes` 峰值。A 若也 0 条，说明症状来自 11-26 那次构建的其它改动（需按提交二分）；A 若复现失败，则 R1/R2 的分工已确认。

## 8. 附录：采样脚本要点

- 用 `ioreg -c IOAccelerator -w0 -l`，只认含 `gartSizeBytes` 的条目；
- 按 `(inUse, free, orphanBytes, orphanCount, hitRate)` 指纹去重，剔除 `...Accum` 与伪条目；
- 每 1 秒采一次（单次耗时约 0.39 s）；
- 判定回收事件：孤儿块数下降 > 40 或字节下降 > 50 MB，同时记录当时的 free / inUse。
